# Clinical Logbook

تطبيق ويب لتوثيق الحالات السريرية بواجهة عربية/إنجليزية، مبني بـ HTML وCSS وJavaScript ومتصل مباشرة بـ Supabase. يستخدم Supabase Auth لتسجيل الدخول، ويعزل بيانات كل مستخدم عبر Row Level Security (RLS).

## المزايا

- إنشاء حساب وتسجيل دخول وخروج باستخدام البريد الإلكتروني وكلمة المرور عبر Supabase Auth.
- **تسجيل دخول تلقائي بعد إنشاء الحساب:** عند نجاح التسجيل يعرض التطبيق لوحة السجل مباشرة. وإذا لم تُرجع Supabase جلسة مباشرة، يحاول التطبيق تسجيل الدخول بالبيانات نفسها تلقائيًا.
- CRUD كامل للحالات: إنشاء، قراءة، تعديل، وحذف.
- الحقول: `patient_code` و`diagnosis` و`notes`، مع التحقق من الطول والمدخلات.
- عرض أحدث 20 حالة مع تاريخ الإنشاء وتاريخ آخر تعديل.
- عزل كامل بين المستخدمين عبر سياسات RLS و`auth.uid()` وعمود `user_id`.
- واجهة عربية (RTL) وإنجليزية (LTR) مع تبديل فوري دون إعادة تحميل الصفحة.
- حفظ تفضيل اللغة فقط في `localStorage` تحت المفتاح `clinical-logbook-language`، دون أي بيانات مرضى.
- واجهة متجاوبة مع الهواتف والأجهزة اللوحية، ودعم تقليل الحركة وإمكانية الوصول.
- فحص تلقائي للمفتاح العام عند فتح الصفحة، مع رسالة واضحة إذا كان المفتاح غير صالح أو لا يطابق رابط المشروع.
- مكتبة Supabase محلية داخل `lib/` مع خطة احتياطية من CDN، لتقليل أعطال الشبكة.
- لا يتم إدراج بيانات المستخدم باستخدام `innerHTML`، بل عبر `textContent`.
- رفض مفاتيح `service_role` و`sb_secret_...` داخل المتصفح.
- مسح قائمة الحالات وبيانات الحساب من DOM عند تسجيل الخروج.

## خطوات الإعداد

### 1) إنشاء الجدول وتفعيل الحماية

افتح مشروعك في [Supabase](https://supabase.com)، ثم:

1. انتقل إلى **SQL Editor**.
2. الصق كامل محتوى `supabase-schema.sql`.
3. اضغط **Run**.

سيتم إنشاء الجدول `clinical_cases`، وتفعيل RLS، ومنع وصول `anon`، وإنشاء سياسات القراءة والإضافة والتعديل والحذف للمستخدم صاحب السجل فقط.

> إذا كان الجدول موجودًا من إصدار قديم، يضيف الملف عمودي `user_id` و`updated_at`. السجلات القديمة التي تحمل `user_id = null` لن تكون مرئية لأي مستخدم. يوجد في نهاية ملف SQL قسم اختياري لترحيلها إلى حساب معيّن.

### 2) إعداد بيانات المشروع

من **Project Settings → API** انسخ:

- **Project URL**
- **anon public key** أو **publishable key**

ثم استبدل القيمتين في `config.js`:

```js
window.CLINICAL_LOGBOOK_CONFIG = {
  supabaseUrl: "https://xxxxxxxxxxxx.supabase.co",
  supabaseAnonKey: "eyJhbGciOi...",
};
```

> استخدم المفتاح العام فقط. لا تضع `service_role` أو `sb_secret_...` في أي ملف يُحمَّل داخل المتصفح. الحماية الفعلية تأتي من RLS وليس من إخفاء المفتاح العام.

> استخدم **Project URL** الأساسي بالشكل `https://PROJECT_REF.supabase.co`، وليس رابط REST المنتهي بـ `/rest/v1/`. التطبيق يتعامل مع الرابط الأخير تلقائيًا، لكن الأساسي هو الصحيح. يجب أن يكون الرابط والمفتاح من المشروع نفسه.

### 3) إعداد المصادقة والدخول التلقائي

من لوحة Supabase:

1. فعّل مزوّد البريد الإلكتروني من **Authentication → Providers → Email**.
2. أضف نطاق التطبيق إلى **Site URL** و**Redirect URLs**. أثناء التطوير يمكن إضافة `http://localhost:5500`.
3. **لتفعيل الدخول التلقائي فور إنشاء الحساب:** اجعل خيار **Confirm email** غير مفعّل. عندها تُرجع Supabase جلسة مباشرة بعد `signUp`، ويدخل المستخدم إلى لوحة السجل فورًا.
4. إذا أبقيت **Confirm email** مفعّلًا، فلن تسمح Supabase بتسجيل الدخول قبل تأكيد البريد. في هذه الحالة يعرض التطبيق رسالة تأكيد البريد، ثم يستطيع المستخدم الدخول بعد الضغط على رابط التأكيد. هذا قيد أمني من Supabase ولا يمكن تجاوزه من واجهة المتصفح، ولا يجوز تجاوزه باستخدام `service_role`.

ماذا يفعل التطبيق بعد التسجيل؟

- إذا أرجع `signUp` جلسة: يفعّل الجلسة ويفتح لوحة السجل مباشرة.
- إذا لم يُرجع جلسة: يحاول `signInWithPassword` تلقائيًا بالبيانات نفسها.
- إذا رفضت Supabase الدخول بسبب تأكيد البريد: ينتقل التطبيق إلى نموذج الدخول ويعبئ البريد تلقائيًا، ثم يطلب تأكيد البريد.
- إذا فشل تسجيل الدخول التلقائي لسبب آخر: يعرض رسالة واضحة مع تعبئة البريد، ويطلب إدخال كلمة المرور مرة واحدة.

### 4) تشغيل الصفحة محليًا

شغّل خادمًا محليًا من مجلد المشروع، مثل:

```bash
python -m http.server 5500
```

ثم افتح:

```text
http://localhost:5500
```

لا تفتح `index.html` مباشرة عبر `file://`؛ لأن Supabase Auth يحتاج أصلًا (origin) صالحًا. يمكنك أيضًا استخدام إضافة Live Server في VS Code، أو نشر الملفات على Netlify أو Vercel أو GitHub Pages.

## اللغة والواجهة

- اللغة الافتراضية عربية، وزر الشريط العلوي يعرض اللغة الهدف (`English` أو `العربية`).
- يتم تبديل `lang` و`dir` على عنصر `<html>`، وتُترجم النصوص الديناميكية والرسائل والتواريخ والأرقام عبر `Intl`.
- يُحفظ تفضيل اللغة فقط في `localStorage` بالمفتاح `clinical-logbook-language`، ويُمسح عند تعذر الوصول إلى التخزين.
- تبديل اللغة لا يعيد تحميل الصفحة، ولا يفقد بيانات النموذج أو وضع التعديل.
- لا تُخزَّن بيانات المرضى في `localStorage` أو `sessionStorage`.

## بنية الجدول

```sql
create table public.clinical_cases (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  patient_code text not null,
  diagnosis text not null,
  notes text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

مع قيود على أطوال الحقول، وفهرس على `(user_id, created_at desc)`، وtrigger يحدّث `updated_at` تلقائيًا. لا ترسل الواجهة `id` أو `created_at` أو `updated_at`؛ تتولى قاعدة البيانات ذلك.

## الأمان والخصوصية

- كل سياسات RLS مرتبطة بـ `auth.uid() = user_id`.
- لا يوجد أي وصول إلى الجدول من دور `anon`؛ القراءة والكتابة للمستخدمين الموثقين فقط.
- لا يستطيع مستخدم رؤية أو تعديل أو حذف سجل مستخدم آخر حتى لو عرف معرّف السجل.
- يتم تصفية الاستعلام بـ `user_id` في الواجهة، وRLS يفرض القيود في قاعدة البيانات كطبقة الحماية الحاسمة.
- لا يتم عرض بيانات السجلات عبر `innerHTML`، ما يمنع حقن HTML من محتوى الحقول.
- الخروج من الحساب يمسح الحالات وبيانات الحساب من DOM ويغلق نافذة الحذف.
- استخدم رموز مرضى بديلة، ولا تدخل الأسماء الكاملة أو أرقام الهوية أو أي بيانات تعريفية مباشرة.
- التطبيق لا يغني عن الالتزام بسياسات مؤسستك وقوانين حماية البيانات الطبية.

## التحقق والاختبار

### اختبار أساسي

1. شغّل الصفحة، وتأكد من ظهور شاشة الدخول بالعربية.
2. أنشئ حسابًا جديدًا.
   - إذا كان تأكيد البريد معطّلًا: يجب أن تظهر لوحة السجل مباشرة دون صفحة دخول وسيطة.
   - إذا كان تأكيد البريد مفعّلًا: يجب أن تظهر رسالة طلب تأكيد البريد.
3. أضف حالة جديدة، ثم عدّلها، ثم احذفها.
4. بدّل اللغة إلى الإنجليزية أثناء التعديل أو أثناء ظهور خطأ، وتأكد من بقاء البيانات وترجمة الرسائل.
5. سجّل الخروج، ثم تحقق من اختفاء الحالات وبيانات الحساب من الصفحة.

### اختبار عزل حسابين

1. أنشئ الحساب الأول وأضف حالة.
2. سجّل الخروج، ثم أنشئ حسابًا ثانيًا.
3. تأكد من أن قائمة الحساب الثاني فارغة ولا تعرض حالة الحساب الأول.
4. حاول الوصول إلى معرّف سجل الحساب الأول مباشرة من Supabase API؛ يجب أن تمنع RLS العملية.
5. سجّل الدخول إلى الحساب الأول وتأكد من ظهور سجله فقط.

### اختبار الإعداد

- إذا بقيت `config.js` بقيم placeholder، يعرض التطبيق شاشة إعداد واضحة بدلًا من محاولة الاتصال.
- عند فتح الصفحة يتحقق التطبيق من المفتاح عبر Supabase؛ فإذا كان المفتاح غير صالح أو لا يطابق رابط المشروع تظهر شاشة إعداد توضح المشكلة.
- إذا لم يُنفّذ SQL، ستظهر رسالة تشير إلى الجدول المفقود أو بنية غير مطابقة.
- إذا استُخدم مفتاح سري، يرفض التطبيق الإعداد قبل إنشاء العميل.

## النشر على GitHub Pages

GitHub Pages يخدم الملفات الثابتة مباشرة، لكن يجب أن تكون الملفات في المكان الصحيح وأن يكون `config.js` صالحًا.

### الخطوات

1. ارفع محتويات مجلد المشروع إلى **جذر المستودع**، وليس داخل مجلد فرعي. يجب أن يكون `index.html` بجانب `app.js` و`config.js` و`styles.css` ومجلد `lib`.
2. من المستودع افتح **Settings → Pages**.
3. تحت **Build and deployment** اختر **Source: Deploy from a branch**.
4. اختر الفرع `main` والمجلد `/ (root)`، ثم اضغط **Save**.
5. انتظر انتهاء عملية النشر، ثم افتح رابط الصفحة:

   ```text
   https://USERNAME.github.io/REPOSITORY/
   ```

6. من Supabase افتح **Authentication → URL Configuration** وأضف رابط GitHub Pages إلى **Site URL** و**Redirect URLs**.

### مهم جدًا

- افتح رابط **GitHub Pages** نفسه، وليس رابط الملف من صفحة GitHub أو رابط `raw.githubusercontent.com`.
- لا تفتح `index.html` مباشرة عبر `file://`.
- إذا كان المستودع باسم `USERNAME.github.io` فسيكون الرابط `https://USERNAME.github.io/`، وإلا فسيكون بالشكل `https://USERNAME.github.io/REPOSITORY/`.
- ملف `.nojekyll` موجود لتعطيل معالجة Jekyll. يُفضّل رفعه مع المشروع، وعدم رفعه لا يمنع عمل الملفات الحالية.
- بعد تعديل `config.js` أو إعادة رفع الملفات، افتح الصفحة ثم اضغط `Ctrl + F5` لمسح النسخة القديمة من الذاكرة المؤقتة.
- إذا كان المستودع خاصًا (Private)، فقد تحتاج إلى خطة GitHub تدعم Pages للمستودعات الخاصة.

### التحقق السريع قبل الرفع

- [ ] `index.html` موجود في جذر المستودع.
- [ ] مجلد `lib` مرفوع ويحتوي `supabase-js.min.js`.
- [ ] `config.js` صالح برمجيًا، وليس فيه رابط ملصق داخل سطر خطأ.
- [ ] `supabaseUrl` و`supabaseAnonKey` من المشروع نفسه.
- [ ] المفتاح `anon` أو `publishable` فقط، وليس `service_role` أو `sb_secret_`.
- [ ] `supabase-schema.sql` نُفّذ في SQL Editor.
- [ ] **Confirm email** معطّل إذا كنت تريد الدخول التلقائي بعد إنشاء الحساب.
- [ ] صفحة GitHub Pages مفعّلة من الفرع والمجلد الصحيحين.

> يمكن نشر الملفات نفسها على Netlify أو Vercel أو أي استضافة ثابتة، مع إضافة نطاق الموقع إلى **Site URL** و**Redirect URLs** في Supabase واستخدام HTTPS. لا تنشر ملفات اختبار محلية أو أي أسرار أو ملفات تحتوي بيانات مرضى.

## الترحيل من إصدار سابق

إذا كان لديك جدول قديم بلا مالك:

1. نفّذ `supabase-schema.sql` لإضافة الأعمدة والسياسات.
2. راجع السجلات التي تحمل `user_id = null` من SQL Editor.
3. خصّصها لحسابك عبر الأمر الاختياري الموجود في نهاية الملف.
4. بعد التأكد من عدم وجود سجلات بلا مالك، يمكنك فرض `NOT NULL` على `user_id`.
